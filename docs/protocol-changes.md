# 协议变更提案流程

依据《项目书》第 6 节：

> 需要修改契约时，创建版本化变更提案，自动列出受影响任务并重建批次。
> **不能让一端私自改字段、另一端仍按旧接口交付。**

---

## 何时需要提案

需要提案：

- 增删改 `packages/protocol/` 中任何 schema 的字段
- 改变字段的必填性、可空性或类型
- 新增或删除错误码
- 新增状态机的转移
- 改变默认参数（时序、上限）
- 改变校验命令或验收基线

不需要提案：

- 修错别字、注释、文档表述（不改语义）
- 新增测试（不放宽已有断言）
- 内部实现重构（不改协议边界）

---

## 提案编号与格式

编号格式 `CP-<四位序号>`，从 `CP-0001` 起。提案文件放在 `docs/proposals/`。

```markdown
# CP-0003：结果报告增加 partial_success 状态

- 提出人：B（OpenCode）
- 提出日期：2026-09-25
- 目标协议版本：v1.1
- 状态：proposed | accepted | rejected | superseded

## 动机
（为什么当前协议无法表达该情况，附实际遇到的证据）

## 变更内容
（精确到字段、类型、必填性；给出前后对比）

## 受影响任务
（列出所有消费该字段的模块与任务 ID，由协调器自动列出后人工核对）

## 兼容性
- [ ] 向后兼容（消费方可忽略新字段）
- [ ] 破坏性变更（需要重建批次与版本号）

## 验收影响
（是否改变验收基线。若是，须说明走独立流程的理由）

## 双方确认
- A（Codex）：
- B（OpenCode）：
```

---

## 处理流程

1. **提案** — 任一方向仓库提交提案文件，**不直接改代码**。
2. **列出影响** — 运行 `npm run validate:protocol`，协调器自动列出受影响任务与批次。
3. **双方确认** — A 与 B 都需在提案文件上签字（PR review）。
4. **落地** — 更新 `packages/protocol/`、更新 `PROTOCOL_VERSION` 的次版本号、
   在 `PROTOCOL_META.changeProposals` 追加提案 ID。
5. **重建批次** — 受影响的任务与批次全部作废，按新契约重新规划。
6. **记录** — 提案文件留在 `docs/proposals/`，不删除。

---

## 破坏性变更

破坏性变更（消费方无法忽略）必须：

- 提升 `PROTOCOL_VERSION` 主版本
- 作废所有进行中的批次
- 明确批准依据
- **不得**由失败任务通过修改契约来自行解决（规则 4）

---

## 禁止事项

- ❌ 一端私自改字段，让另一端按旧接口交付
- ❌ 通过修改协议放宽自己的验收门槛
- ❌ 在任务执行途中"悄悄"切换到另一版本契约
- ❌ 删除已接受的提案文件
